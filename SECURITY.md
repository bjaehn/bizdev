# Security review notes: SEI Chicago BD Signal Agent

Prepared for SEI IT review. Everything here describes what the code in this repository does today.
Where something is a gap or could not be verified, it says so (see **Known gaps**).

**Purpose.** Weekly, public-source research on Chicagoland companies showing demand for SEI's
services, producing a scored shortlist as a Microsoft Teams card. Research only: it drafts no
outreach and contacts no one. No LinkedIn and no paywalled sites (a domain blocklist in
`config.yaml` is applied to both searching and fetching).

## 1. External services and the data sent to each

| # | Service | Host(s) | Data sent | When |
|---|---------|---------|-----------|------|
| 1 | **Anthropic API** (Claude, with Anthropic's hosted web search tool) | `api.anthropic.com` | See 1a-1d below | Every scan, enrich and card run |
| 2 | **Public websites** (source-URL verification) | Any public host that appears in search results, except blocked domains | An HTTP GET for the URL, plus the `User-Agent` header (`BD_USER_AGENT`, which contains a contact email). No cookies, no credentials, no body. Only the status line and headers are read; the page body is never downloaded | Each candidate source URL, each proposed company domain |
| 3 | **SEC EDGAR** | `data.sec.gov`, `www.sec.gov` | A company's CIK and filing identifiers in the URL, plus the `User-Agent` header | Only for accounts that have a CIK |
| 4 | **Microsoft Teams** incoming webhook / Workflows | Host inside `TEAMS_WEBHOOK_URL` (a secret) | The Adaptive Card JSON (see 4a) | Only if `TEAMS_WEBHOOK_URL` is set and `--dry-run` is not given |
| 5 | **GitHub** (only if you use the provided Actions workflow) | `github.com` | Repository contents, secrets and variables, run logs, the saved database (see 5a) | Weekly, and on manual dispatch |
| 6 | **PyPI** (install time only) | `pypi.org` | Package download requests | `pip install` |

### 1. Anthropic API: exactly what is in each request

The request body is the only thing sent; the API key travels in the standard header.

* **1a. Web-search scanners (`leadership`, `events`, `pe`, `hiring`, `tech_procurement`)**: a static system prompt,
  plus per company: company name, website domain (if known), HQ city (if known), today's date, and the
  window (180 days; 60 days for job postings). The `pe` scanner also sends the PE sponsor's name if you
  recorded one, and runs only for accounts marked PE-backed. The web search
  tool is enabled with the blocked-domain list; searches are generated by the model and executed by
  Anthropic. Search results (public pages) come back into the model context.
* **1b. SEC filing reader (`edgar`)**: company name, form type, filing and report dates, and an excerpt of
  the filing (at most 8,000 characters, starting at Item 5.02). Public SEC text. No web search.
* **1c. `bd enrich`**: company name, known domain, known HQ city, today's date. Web search enabled.
* **1d. Briefer (`bd card`)**: company name, industry, and up to 4 signals (type, event date, days ago,
  confidence, the stored 25-word summary, role/person name, service lines) for leads already chosen for
  the card. No score, no URLs, no web search.

Not sent to Anthropic: the exclusions list, client names, revenue/employee figures, scores, the database,
API keys, or any SEI internal data. Names of executives appear only where a public source named them
(e.g. "Pat Lee, CIO").

*Retention and training terms for this API traffic depend on SEI's agreement with Anthropic and are not
configured by this code. IT should confirm them.*

### 4a. Teams card contents
Company names, band and score, the one-sentence why-now line, best service line, industry / HQ city /
ownership / PE sponsor (where known), the strongest signals (type, date, confidence, role/person), and
links to public source URLs. The card has link buttons only (`Action.OpenUrl`); there are no inputs or
submit actions. Anyone who holds the webhook URL can post to that channel, so treat it as a secret.

### 5a. GitHub (optional deployment)
* Secrets: `ANTHROPIC_API_KEY`, `TEAMS_WEBHOOK_URL` (repository secrets). Variables: `ANTHROPIC_MODEL`,
  `BD_USER_AGENT`. Secrets are exposed only to the single workflow step that runs the weekly script.
* **State branch `bd-state`**: the SQLite database (target accounts, signals, scores, cooldowns, token and
  cost log) is stored as a single force-pushed commit so cooldowns survive between runs. This is the
  firm's BD pipeline: **the repository must be private with restricted access**, or use the cron
  deployment on an SEI-managed host instead.
* The last `card.json` is kept as a workflow artifact for 30 days.
* Workflow run logs print account names, counts, token counts and estimated cost (never secrets).
* `permissions: contents: write` is used only by `scripts/state.sh` to update `bd-state`; checkout is
  configured with `persist-credentials: false`, so the token is not left in git config for other steps.

## 2. Data stored locally

One SQLite file (default `bd.sqlite`, not encrypted). Tables: `accounts` (facts you entered or approved),
`signals` (public-source summaries and URLs), `scores`, `briefs`, `exclusions` (**client / do-not-pursue
names: confidential**), `runs` (tokens, estimated cost, error text). `exclusions.csv` and `accounts.csv`
in the repository hold the same account and exclusion information. Excluded and held accounts are never
sent to Anthropic, EDGAR or Teams. Deleting the file deletes everything the system has learned.

`config.yaml` holds weights, thresholds, counties, size floors, the blocked-domain list and prices, and no
secrets (a test asserts this).

## 4. Controls implemented

* **No fabricated sources.** A signal is stored only if its URL was returned by the search tool in that
  same call *and* a code fetch of the URL succeeds. SEC filings come from EDGAR itself.
* **Source confidence is reconciled by code** against the URL's real domain; the model can lower
  confidence but never raise it.
* **Fetch safety.** Only http(s); every redirect hop is re-checked (max 5); blocked domains and
  private/loopback/link-local addresses are refused; request timeouts; body never read.
* **Blocked domains** (LinkedIn and common paywalled sites) are excluded from search and from fetching.
* **Prompt-injection posture.** Web and filing text is treated as data in every prompt, and the model's
  output is only ever JSON validated by code (types, dates in window, 25-word summaries, allowed service
  lines, one-sentence why-now with no figures that are not in the stored signals). Nothing the model
  writes is executed or used to choose a URL to act on. The Teams card cannot trigger any action.
* **Fit gate.** Anything unverifiable (location, size) is held and never scanned, scored or posted.
* **Spend limits.** Per-run soft budget cap (`llm.max_cost_per_run_usd`), bounded concurrency, SEC
  requests spaced out (about 6 per second against the SEC's published limit of 10).
* **Posting safety.** Default is a dry run. A post happens only if the webhook is set; a lead is marked
  posted only after Teams accepts the card. The scheduled script stops at the first failed step.
* **Reviewable proposals.** `bd enrich` writes a CSV with an evidence URL per fact and never writes to the
  database; a person reviews it before it is loaded.

## 5. Known gaps and limits

1. **Not yet exercised live.** The code was built and tested offline (fake LLM, fake HTTP). It has not yet
   run against the live Anthropic API, live EDGAR, live websites or a real Teams webhook. The EDGAR
   submissions JSON layout is implemented as documented and parsed defensively but could not be fetched
   to confirm. Treat the first runs as supervised.
2. **A resolving URL is not proof the page supports the claim.** Code proves the URL was retrieved and
   loads. For web-search signals, whether the page actually says what the summary says rests on the model
   (the evaluation harness against a human-verified gold file exists to measure this).
3. **Verification fetches go to arbitrary public hosts**, so egress cannot be allowlisted by host. A
   DNS-rebinding race between the address check and the connection is not closed.
4. **Prompt injection cannot be ruled out.** The controls above limit the effect to an incorrect or
   missing signal, but a hostile page could still skew a summary.
5. **No lockfile.** Dependencies (`anthropic`, `httpx2`, `pydantic`, `pyyaml`, `typer`, `tzdata`) resolve to
   the latest compatible versions at install time. Pin and scan them before production use.
6. **GitHub Actions are referenced by tag** (`actions/checkout@v4`, `setup-python@v5`, `upload-artifact@v4`),
   not by commit SHA.
7. **The database is unencrypted** and relies on file or repository permissions.
8. **No prompt-level audit trail.** The `runs` table keeps counts, tokens, cost and error text, not the
   full prompts and responses.
9. **The blocklist is a starter list** of domains (LinkedIn, common paywalled news sites, and the Indeed,
   Glassdoor and ZipRecruiter job boards), not a complete paywall or social-media inventory.
10. **Job-posting dates are read from pages by the model** (a page that says "posted 5 days ago" is converted
    to a date). Code verifies the URL and window but cannot independently confirm a posting's date.

## 6. Decisions for IT

* Approve or restrict egress: `api.anthropic.com`, `data.sec.gov`, `www.sec.gov`, the Teams webhook host,
  and (hard to allowlist) arbitrary public hosts for URL verification, perhaps through an inspecting proxy.
* Confirm Anthropic data-retention terms for this use.
* Choose the deployment: GitHub Actions (private repo, state branch) or an SEI-managed host with cron.
* Decide who may hold the Teams webhook URL and where the API key is stored (secret manager vs repo secret).
* Decide dependency pinning and scanning, and Actions SHA pinning.
